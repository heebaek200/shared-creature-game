## 1. 테스트 결과
### TC-38-01 / PASS — WebSocket 연결

크리처 화면에 현재 상태가 정상 표시됐다. Chrome DevTools의 WebSocket 메시지 목록에서 서버의 STOMP `CONNECTED` 응답을 확인.

같은 WebSocket 연결에서 동일 그룹의 `/live`와 `/chat`을 각각 하나씩 구독함을 확인.


### TC-38-02 / BLOCKED — 실시간 데이터 반영

#### CASE 1. 이미 크리처가 부화한 그룹 / PASS
(1) 같은 계정 / (2) 동일 그룹의 다른 계정 으로 크리처 화면을 두 탭에서 열어서 진행.

한 탭에서 퀘스트를 완료하자 다른 탭의 크리처 상태가 새로고침 없이 갱신되었으며 채팅도 마찬가지로 적용됨.

Chrome DevTools의 WebSocket 메시지 목록에서도 /live와 /chat에 대한 서버 `MESSAGE` 수신을 확인. 연결당 같은 그룹의 두 목적지를 각각 하나씩 허용하는 API 설계와 일치했다.

#### CASE 2. 크리처가 아직 부화하지 않은 그룹 / BLOCKED
동일 그룹의 다른 계정으로 크리처 화면을 두 탭에서 열어서 진행.
- **버그 · 부화 전 직접 확인 퀘스트 완료 차단**

    별도 시도에서 공통 시즌이 진행 중이고 크리처가 알 상태인 그룹으로 접속해, 마감 전에 ‘10분 독서’ 퀘스트의 **완료하기**를 눌렀음.

    설계상 퀘스트가 완료되고 크리처 경험치와 개인 기여도가 누적되어야 하나, 실제로는 서버가 HTTP `409`, 오류 코드 `QUEST_PERIOD_ENDED`, 상세 메시지 “그룹 시즌이 활성 상태가 아닙니다.”를 반환.

    직접 완료 로직은 부화 후에 설정되는 `GroupSeasonStatus.ACTIVE`를 요구하는 상태임. 공통 시즌과 퀘스트 기간이 유효하고 나머지 완료 조건을 충족하면, 부화 전(`PREPARING`)에도 완료와 보상 누적이 가능해야 함

    이 시도에서는 완료 요청이 거절되어 실시간 반영을 검증할 수 없었음.

  - **개선 제안** — 시즌 활성 여부를 판정하는 데 `GroupSeasonStatus.ACTIVE` 대신 공통 시즌의 `SeasonStatus.ACTIVE`를 사용. 공통 시즌이 활성 상태이고 퀘스트의 유효 기간과 나머지 완료 조건을 충족하면, 부화 전에도 퀘스트 완료와 경험치·기여도 누적을 허용.


- **사용자 경험(UX) · 퀘스트 완료 거절 사유가 잘못 표시됨**
  
  같은 시도에서 카드에 표시된 마감까지 시간이 남아 있었으나, 화면에는 “퀘스트 기간이 종료되었습니다.”가 표시됨. 서버의 상세 메시지는 “그룹 시즌이 활성 상태가 아닙니다.”임을 확인.
  
  화면은 서버의 상세 메시지보다 `QUEST_PERIOD_ENDED`에 연결된 문구를 우선 표시. 부화 전 완료 차단을 수정하면, 이번 재현 조건에서는 퀘스트가 정상 완료되어 해당 안내도 표시되지 않을 것으로 예상됨.


### TC-38-03 / PASS — 새로고침 후 복원

Chrome에서 크리처 화면을 새로고침 후 최신 크리처 상태가 정상 표시됐다.

채팅 말풍선이 표시되는 5초 이내에 새로고침했을 때 기존 말풍선이 사라짐을 확인. 이는 새로고침 후 이전 채팅을 복원하지 않는 화면 설계와 일치하는 결과임을 확인.


### TC-38-04 / PASS — 화면 이동 후 복귀

Chrome에서 크리처 화면을 벗어나 다른 페이지로 이동한 뒤, 다시 크리처 화면으로 돌아옴.

복귀한 화면에 최신 크리처 상태가 정상 표시됨을  확인.


### TC-38-05 / PASS — 다른 그룹으로 이벤트 전달 차단

Chrome 일반 창에서 계정 A로 같은 그룹의 크리처 화면을 두 탭에 열고, 시크릿 창에서 계정 B로 다른 그룹의 크리처 화면을 열어서 진행.

탭 1에서 퀘스트를 완료하자 같은 그룹의 탭 2에서 `/live` 서버 메시지 2건을 수신했다. 다른 그룹의 탭 3에는 해당 퀘스트 완료 이벤트가 전달되지 않음을 확인.


### TC-38-06 / PASS — 새로고침 후 아바타 복귀

Chrome 일반 창과 시크릿 창에서 서로 다른 두 계정으로 같은 그룹의 크리처 화면을 열어서 진행.

계정 A의 크리처 화면을 새로고침하자, 계정 B의 화면에서 A의 아바타가 잠시 사라졌다가 새로고침이 끝난 뒤 B의 화면을 새로고침하지 않아도 A의 아바타가 다시 표시됨.

새로고침 중 일시 퇴장은 허용된 동작이다.


### TC-38-07 / PASS — 동일 계정 다중 탭에서 아바타 중복 표시 방지

Chrome 일반 창의 두 탭에서 같은 계정 A로 동일 그룹의 크리처 화면을 열어서 진행. 시크릿 창에서는 같은 그룹에 속한 별도 계정 B로 크리처 화면을 열어 관찰.

계정 A가 두 탭에 동시에 접속해도 계정 B의 화면에는 A의 아바타가 하나만 표시됨을 확인.


### TC-38-08 / PASS — 마지막 WebSocket 연결 종료 시 아바타 제거

Chrome 일반 창의 두 탭에서 계정 A로 같은 그룹의 크리처 화면을 열어서 진행. 시크릿 창에서는 같은 그룹의 계정 B로 접속해 A의 아바타를 관찰.

A의 탭 하나를 닫았을 때 B의 화면에 A의 아바타가 계속 표시되었으며, A의 마지막 탭을 닫자 B의 화면에서 새로고침 없이 A의 아바타가 즉시 사라짐.


### TC-38-09 / PASS — WebSocket 장애 시 30초 REST 동기화

Chrome에서 크리처 화면을 한 탭에 열어서 진행. 로컬 Vite의 `/ws` 프록시 대상을 사용하지 않는 포트로 임시 변경해 WebSocket 연결 장애를 재현.

장애 상태에서 헤더에 `30초 동기화 중`이 표시. 이후 화면을 새로고침하지 않고 관찰하자 `creature-home` REST 요청이 약 30초 간격으로 발생했고 HTTP `200`을 반환.

**미검증** — 페이지를 유지한 상태에서 WebSocket이 자동 재연결되고 REST 폴링이 중단되는지는 확인하지 않았음.


### 추가 발견 사항
**버그 · 가상 데스크톱 복귀 후 아바타 걷기 애니메이션이 간헐적으로 멈춤**

발견 시점 : Chrome에서 공동 크리처 화면에서 아바타 이동을 ON으로 설정 후, 창을 열어둔 상태로 `Ctrl + Win + ←/→`를 눌러 다른 가상 데스크톱으로 이동한 뒤 돌아오는 경우에 발견.

현상 : 복귀 후 아바타가 간헐적으로 같은 자세(stop- 이미지)를 유지한 채 미끄러지듯 이동함. 종종 속도 또한 빠르게 적용됨.

기타 : 데스크톱 복귀 직후 종종 관찰되었으나, 항상 재현되지는 않았다.
