# 요구사항

## 1. 의뢰인 배경

의뢰인은 생활 습관 형성형 소셜 게임의 가능성을 검증하려는 스타트업 서비스 기획자입니다. 4명의 개발자가 약 2주 안에 핵심 게임 흐름과 서버 기술 요소를 시연할 수 있는 웹 기반 MVP 제작을 요청했습니다.

## 2. 프로젝트 목적

작은 일상 활동을 지속할 동기가 필요한 사용자가 공개 그룹에 참여하여 다른 사용자와 공동 목표를 공유하고, 일일·주간 퀘스트를 수행하며 하나의 크리처를 함께 성장시키는 경험을 제공합니다.

적극적인 SNS 교류를 요구하지 않으면서도 개인 기여도와 그룹 성과를 확인할 수 있게 하여 느슨한 협력과 경쟁의 동기를 함께 제공합니다. 사회적 고립 감소, 야외 활동 증가와 생활 습관 개선은 서비스가 지향하는 가설적 기대 효과이며 MVP의 검증된 효과로 주장하지 않습니다.

## 3. 대상 사용자

- 작은 일상 활동을 시작하거나 지속할 동기가 필요한 사용자
- 가벼운 육성 게임과 경쟁 요소를 즐기는 사용자
- 낯선 사용자와도 부담이 적은 공동 목표를 공유하고 싶은 사용자
- 별도 모바일 애플리케이션 설치 없이 웹 브라우저에서 서비스를 이용하려는 사용자

서비스 참여 범위는 친구나 지인 초대에 한정하지 않고 가입 사용자 전체에 개방합니다.

## 4. 필수 기능

### 4.1. 계정과 사용자

- 회원가입과 로그인은 구글·네이버 소셜 로그인만 지원합니다.
- 자체 이메일·비밀번호 회원가입과 비밀번호 저장·재설정 기능은 제공하지 않습니다.
- 프론트엔드는 Full CSR로 구성하고 백엔드는 화면 HTML이 아닌 REST API와 OAuth 콜백을 제공합니다.
- 비로그인 사용자의 현재 사용자 응답은 `ANONYMOUS + NOT_STARTED`, OAuth를 마친 가입 대기 사용자는 `SIGNUP_PENDING + SIGNUP_REQUIRED`로 구분합니다.
- 프론트엔드는 React·Vue 같은 UI Framework 없이 Vanilla JavaScript ES Module과 Vite로 구성합니다.
- UI·반응형 CSS Framework는 Bootstrap v5를 사용합니다.
- 소셜 계정은 공급자와 공급자가 발급한 사용자 식별자의 조합으로 식별합니다.
- 동일 이메일로 다른 소셜 공급자 계정이 존재해도 자동 연결하지 않고 기존에 가입한 공급자로 로그인하도록 안내합니다.
- OAuth 인가 코드는 백엔드가 콜백으로 받아 서버 간 토큰 교환을 수행하고 애플리케이션 로그인은 서버 세션으로 유지합니다.
- OAuth 로그인 시작 시 익명 세션을 만들고 로그인 시도에는 시작 세션 ID의 SHA-256 Hash를 보관합니다. Callback의 세션이 다르면 로그인을 중단하고 처음부터 다시 시작하게 합니다.
- 세션은 마지막 요청부터 7일 동안 활동이 없으면 만료합니다.
- 사용자당 동시 로그인 세션은 최대 3개이며 초과 로그인 시 가장 오래된 세션을 종료합니다.
- 신규 가입에는 공급자가 제공하는 이메일이 필요하며 이메일 제공에 동의하지 않았거나 이메일을 제공받지 못하면 가입을 중단합니다.
- 기존 회원은 공급자와 공급자 사용자 식별자가 일치하면 이후 이메일 제공 상태와 관계없이 로그인할 수 있습니다.
- 네이버 로그인은 개발 단계에서 팀원 4명의 계정을 관리자 또는 테스터로 등록해 구현과 시연에 사용합니다.
- 네이버 사전 검수 전에는 등록된 관리자·테스터 계정만 로그인할 수 있으며, 모든 네이버 사용자가 로그인하는 공개 운영 전에는 네이버 사전 검수를 통과해야 합니다.
- 일반 회원가입을 완료하면 별도의 그룹 선택 페이지로 이동합니다.
- 그룹 선택 페이지는 신규 가입자와 탈퇴·강퇴 후 24시간 제한이 끝난 사용자가 그룹을 선택하는 공통 화면입니다.
- 그룹이 없는 사용자는 그룹 선택 페이지에서 기존 공개 그룹에 가입하거나 새 그룹을 생성할 수 있습니다.
- 새 그룹을 생성한 사용자는 해당 그룹의 주 관리자가 됩니다.
- 사용자는 자신을 표현하는 아바타와 보유한 꾸미기 아이템을 확인할 수 있습니다.
- 아바타 아이템은 프로젝트의 주 수입원이므로 장착 결과를 다른 그룹 구성원에게 보여줄 수 있어야 합니다.
- 기본 과시 공간은 크리처 홈이며, 현재 접속한 그룹 구성원의 아바타가 공동 크리처 주변을 돌아다니는 구성을 우선 설계합니다.
- 전체 관리자, 주 관리자, 부 관리자와 일반 사용자의 권한을 구분합니다.
- 전체 관리자는 여러 그룹을 관리할 수 있습니다.
- 최초 전체 관리자는 공개 API로 생성하지 않습니다. 활성 전체 관리자가 없을 때 서버 환경변수에 지정한 소셜 공급자와 공급자의 불변 사용자 ID가 모두 일치하는 신규 계정이 가입할 때만 `SUPER_ADMIN`을 부여합니다.
- 그룹 최초 생성자는 해당 그룹의 주 관리자가 되며 그룹당 주 관리자는 1명입니다.
- 주 관리자 권한을 다른 활성 회원에게 이전하면 대상은 `PRIMARY`, 기존 주 관리자는 `MEMBER`가 됩니다.
- 한 그룹에는 여러 부 관리자를 둘 수 있습니다. 주 관리자는 같은 그룹의 일반 사용자에게 부 관리자 권한을 부여하거나 회수할 수 있습니다.
- 부 관리자는 일반 사용자를 관리할 수 있지만 관리자 권한을 부여하거나 회수할 수 없습니다.
- 부 관리자는 마지막 인증 활동 후 72시간이 지난 일반 회원만 강퇴할 수 있으며 주 관리자나 다른 부 관리자를 강퇴할 수 없습니다.
- 주 관리자는 역할과 관계없이 마지막 인증 활동 후 72시간이 지난 주 관리자가 아닌 회원을 강퇴할 수 있습니다.
- 마지막 인증 활동은 로그인 성공 또는 인증된 API 요청 성공으로 갱신하며, 요청이 잦아도 최대 10분에 한 번만 영속화합니다. 저장 지연으로 실제 72시간 미경과 회원을 강퇴하지 않도록 서버 판정은 저장된 시각에서 `72시간 10분`이 지난 경우에만 허용합니다.
- 주 관리자는 부 관리자 권한을 언제든 회수할 수 있지만, 부 관리자를 그룹에서 강퇴하려면 다른 회원과 동일한 72시간 미활동 조건을 충족해야 합니다.

### 4.2. 그룹과 공동 육성

- 공개 그룹은 최대 20명이 참여할 수 있고 전체 관리자는 여러 그룹을 관리할 수 있습니다.
- 가입 사용자는 정원이 남은 공개 그룹을 직접 선택하여 별도 승인 없이 참여할 수 있습니다.
- 그룹 생성 시 회원가입과 그룹 가입을 연결하는 공유 링크를 자동 생성하며 사용 횟수를 제한하지 않습니다.
- 자동 생성 링크는 만료되지 않으며 재발급하면 기존 링크는 즉시 무효화됩니다.
- 가입 링크 재발급 권한은 주 관리자만 가집니다.
- 링크를 받은 미가입자는 그룹 가입을 수락한 뒤 구글 또는 네이버 인증을 완료해야 회원가입이 완료됩니다. 거절하면 계정을 생성하지 않고 일반 소셜 로그인·회원가입 화면으로 이동합니다.
- OAuth 콜백은 신규 사용자의 계정을 생성하지 않고 검증한 소셜 정보와 초대 문맥을 서버의 가입 대기 세션에 저장한 뒤 회원가입 페이지로 이동시킵니다. 가입 대기 세션은 콜백 완료 시점부터 30분 동안만 유효하며 활동으로 연장되지 않습니다.
- 가입 대기 세션이 만료되면 계정을 생성하지 않고 대기 정보를 폐기한 뒤 로그인 페이지에서 소셜 인증을 다시 시작하도록 안내합니다.
- 링크 수락 후 회원가입 제출 시 계정을 생성하기 직전에 링크 유효성, 그룹 정원, 기존 소속과 탈퇴·강퇴 후 24시간 제한을 다시 검사합니다.
- 재검사에서 그룹 가입 조건을 충족하지 못해도 계정은 생성하며, 실패 이유를 표시하고 그룹 선택 페이지로 이동합니다.
- 기존 가입자가 링크를 수락하면 새 계정을 만들지 않습니다. 그룹이 없으면 링크·정원·24시간 제한을 검사해 초대 그룹에 즉시 가입하고, 이미 그룹이 있거나 조건을 충족하지 못하면 가입하지 않고 실패 이유를 표시합니다.
- 전체 관리자는 신고를 근거로 사용자를 그룹에서 강퇴할 수 있고, 그룹 관리자는 3일 이상 접속하지 않은 사용자를 담당 그룹에서 강퇴할 수 있습니다.
- 일반 사용자는 자신의 그룹에서 직접 탈퇴할 수 있습니다.
- 주 관리자가 유일한 구성원이면 같은 탈퇴 동작으로 그룹을 비활성화하고 초대 링크와 현재 시즌 참여를 종료합니다. 기록은 보존하고 별도 해산 화면과 API는 추가하지 않습니다.
- 각 그룹은 활성 크리처 1마리를 공동으로 육성하며 개인별 크리처는 MVP에 포함하지 않습니다.
- 공동 크리처는 4주 시즌마다 교체하며, 그룹이 해당 시즌에 참여하기 시작한 시각부터 3일 동안 알 상태로 유지합니다.
- 모든 일정 기준은 `Asia/Seoul` 시간대를 사용합니다. 서비스는 첫 시즌 시작 월요일 0시에 공개하며 공개 시각과 첫 시즌 시작 시각을 일치시킵니다.
- 주 관리자와 부 관리자는 그룹의 시즌 참여 시작 후 `3 × 24시간` 동안 시작 크리처를 선택하거나 변경할 수 있습니다.
- 그룹은 시즌 중에도 생성할 수 있으며 생성 즉시 현재 시즌에 참가하고 알 상태의 공동 크리처를 생성합니다.
- 그룹의 시즌 참여 시작 후 `3 × 24시간` 안에 관리자가 시작 크리처를 정하지 않으면 무작위 크리처로 부화합니다.
- 시즌 종료 시 크리처 최종 상태와 시즌 랭킹을 보존합니다. 새 시즌에는 크리처 경험치, 시즌 기여도와 시즌 그룹 점수를 초기화하지만 회원, 그룹, 아이템과 누적 활동 기록은 유지합니다.
- 시즌 종료는 `SEASON_CLOSE` Scheduler가 한 번만 처리하며 크리처 보관, 개인·그룹 최종 랭킹 Snapshot과 시즌 종료 상태를 확정한 뒤 다음 시즌을 시작합니다.
- 크리처 성장 단계는 `알 → 유년기 → 성장기 → 성숙기 → 완전체`로 구성합니다.
- 유효한 일일·주간 퀘스트 완료만 크리처 경험치를 지급하며 결제, 초대와 관리자 조작으로는 경험치를 지급하지 않습니다.
- 퀘스트별 크리처 경험치와 개인 기여도 점수를 별도로 설정합니다.
- 그룹 누적 경험치 기준 유년기 0, 성장기 45,000, 성숙기 97,500, 완전체 150,000을 적용합니다.
- 크리처 경험치는 완전체 기준을 넘어서도 제한 없이 누적하며 개인 기여도와 그룹 점수도 계속 누적합니다.
- 사용자의 퀘스트 성과를 그룹 크리처의 경험치와 성장 상태에 반영합니다.
- 크리처의 기본 성장과 진화는 유료 구매를 조건으로 하지 않습니다.
- 그룹 내 개인 기여도 랭킹과 그룹 간 랭킹을 제공합니다.
- 개인 기여도는 퀘스트별 기여도 점수의 시즌 합계로, 그룹 점수는 소속 사용자들의 시즌 기여도 합계로 계산합니다.
- 결제 금액과 아이템 구매는 개인·그룹 랭킹에 반영하지 않습니다.
- 개인·그룹 랭킹은 새 시즌에 0으로 초기화하고 종료된 시즌 랭킹은 조회 가능한 기록으로 보존합니다.
- 동점이면 해당 점수에 먼저 도달한 대상을 상위로 두고 도달 시각도 같으면 ID 오름차순으로 순서를 고정합니다.

### 4.3. 퀘스트와 보상

- 일일·주간 퀘스트를 제공하고 서버가 완료 조건을 판정합니다.
- 일일 퀘스트는 `Asia/Seoul` 기준 매일 0시에, 주간 퀘스트는 월요일 0시에 갱신합니다.
- 시스템은 개발자가 정의한 순회 규칙에 따라 퀘스트 템플릿에서 일일 3개와 주간 7개를 선정해 모든 사용자에게 동일하게 배정합니다.
- 개발자는 일일 템플릿을 하 5개·중 4개·상 3개, 주간 템플릿을 하 6개·중 4개·상 4개 이상 활성 상태로 준비합니다.
- 일일 퀘스트는 하·중·상 각 1개, 주간 퀘스트는 하 3개·중 2개·상 2개로 구성합니다.
- 관리자 역할은 퀘스트 배정 목록을 수동으로 선택하지 않습니다.
- 각 퀘스트는 사용자당 해당 일일·주간 기간에 한 번만 완료할 수 있고 다음 기간으로 이월하지 않습니다.
- 같은 기간에는 동일한 템플릿을 중복 배정하지 않으며 다음 기간에는 순회 규칙에 따라 다시 배정할 수 있습니다.
- 순회 인덱스는 첫 시즌 시작 시각을 0으로 하는 `Asia/Seoul` 누적 일수·주차를 사용하며 시즌이 바뀌어도 초기화하지 않습니다.
- 일일 난이도별 시작 오프셋은 하 0·중 1·상 2이고, 주간 시작 오프셋도 하 0·중 1·상 2를 사용합니다.
- 배정 시 템플릿 버전, 문구, 난이도, 완료 조건, 보상과 기여도 값을 Snapshot으로 저장하며 진행 중인 기간에는 템플릿 수정 내용을 반영하지 않습니다.
- 기술 검증 중인 템플릿은 `EXPERIMENTAL`로 분류하고 활성화되기 전까지 순회 대상에서 제외합니다.
- 퀘스트 검증 유형은 사용자 완료 확인형 `SELF_CHECK`, 서버 행동 기록형 `SERVER_EVENT`, 기간 집계형 `AGGREGATE`, 사진 메타데이터형 `PHOTO_EXIF`로 구분합니다.
- 일반 생활 활동은 `SELF_CHECK`, 서비스 안에서 관찰 가능한 행동은 `SERVER_EVENT`, 주간 누적 조건은 `AGGREGATE`를 우선 사용합니다.
- `PHOTO_EXIF`는 MVP 핵심 필수 기능이며 활성 순회 대상에서 제외할 수 없습니다.
- Android Chrome과 iOS Safari 실기기에서 GPS와 촬영 시각 추출, 실패 안내와 파일 정리까지 검증해야 하며 검증 실패는 기능 제외 사유가 아니라 MVP 미완료로 처리합니다.
- 관리자 수동 승인과 사후 증빙 제출은 MVP에 포함하지 않습니다.
- 모든 유형은 서버가 활성 배정, 수행 기간, 사용자와 그룹 상태, 중복 완료 여부를 검사하고 Snapshot에 저장된 보상만 지급합니다.
- 기간 집계형 퀘스트는 활동 발생 당시 멤버십·그룹 시즌이 완료 시점의 활성 멤버십·그룹 시즌과 같은 기록만 사용하며 이전 그룹 활동을 새 그룹 보상에 포함하지 않습니다.
- 완료된 퀘스트는 사용자가 취소하거나 다른 템플릿으로 변경할 수 없습니다.
- 서비스 체크인은 사용자가 명시적으로 실행하는 하루 1회 행동이며 단순 페이지 조회로 기록하지 않습니다.
- 오전 기상 체크인은 `Asia/Seoul` 기준 05:00 이상 09:00 미만에 완료한 서비스 체크인입니다.
- 활성 일일 템플릿은 물 마시기, 스트레칭, 정리, 독서, 호흡·휴식, 기상 체크인, 걷기, 집중 활동, 운동과 당일 하·중 퀘스트 완료로 구성합니다.
- 활성 주간 템플릿은 서비스 체크인 일수와 일일 퀘스트의 횟수·난이도·수행 일수·하루 전체 완료를 집계하는 조건으로 구성합니다.
- 위치 사진 일일·주간 템플릿은 중 난이도 활성 템플릿으로 순회합니다.
- 필요한 난이도별 템플릿이 부족하면 해당 기간의 배정 생성을 실패 처리하고 전체 관리자에게 부족한 난이도와 개수를 알립니다.
- 일일 퀘스트는 크리처 경험치 100, 주간 퀘스트는 크리처 경험치 300을 지급하여 사용자 1명이 일주일에 받을 수 있는 최대 크리처 경험치는 4,200입니다.
- 퀘스트는 난이도 상·중·하 배점을 가집니다.
- 난이도는 크리처 경험치에 영향을 주지 않고 개인 기여도에만 반영합니다.
- 일일 퀘스트 기여도는 하 10·중 20·상 30, 주간 퀘스트 기여도는 하 30·중 60·상 90입니다.
- 그룹별 알 상태의 첫 3일에도 퀘스트 경험치와 개인 기여도를 누적하고 부화 시 누적 경험치를 적용해 도달한 성장 단계로 즉시 전환합니다.
- 기상 체크인과 EXIF GPS·촬영 시각을 이용한 야외 사진 인증을 퀘스트에 포함합니다.
- GPS 정보가 없는 사진은 위치 인증 실패로 처리하며, 대체 인증과 예외 승인은 이번 범위에 포함하지 않습니다.
- 사진 업로드 형식은 최대 10 MiB의 JPEG만 허용합니다. HEIC·HEIF와 그 밖의 형식은 지원하지 않으며 서버가 MIME 형식과 JPEG 파일 Signature를 함께 검사합니다.
- 사진 제출은 사용자·퀘스트 배정당 최대 5회, 사용자당 1분에 최대 5회로 제한합니다. EXIF 메타데이터는 최대 1 MiB이며 픽셀 전체를 디코딩하지 않고 전용 실행기에서 최대 4건을 5초 안에 병렬 판정합니다.
- EXIF 판정은 위도·경도와 촬영 시각의 존재, 좌표의 유효 범위, 촬영 시각이 배정 시작 이상·종료 미만인지까지만 검사합니다. EXIF 시각에 Offset이 없으면 `Asia/Seoul`로 해석합니다.
- 사진은 EXIF 촬영 시각과 서버 업로드 접수 시각이 모두 배정 기간 안이고 판정·보상 트랜잭션이 배정 종료와 시즌 `CLOSING` 전에 Commit된 경우에만 보상합니다. 마감 유예시간과 다음 기간 이월은 제공하지 않습니다.
- 실외 여부, 현재 기기 위치와의 일치, 목표 장소·반경, 사진 간 거리, 메타데이터 위변조와 동일 사진 재사용은 MVP에서 판정하지 않습니다.
- 중복 제출과 동시 요청으로 보상이 중복 지급되거나 그룹 경험치 갱신이 유실되지 않게 동시성을 제어합니다.

### 4.4. 실시간 기능

- 서버에서 확정한 크리처 성장, 개인 기여도와 그룹 상태 변경을 WebSocket으로 관련 사용자에게 전달합니다.
- WebSocket 메시지는 업무 결과를 확정하지 않고 서버에서 완료된 처리 결과를 전파하는 용도로 사용합니다.
- STOMP 인바운드는 기본 거부하고 세션·허용 Origin·CSRF를 검증한 `CONNECT`, 현재 활성 그룹 목적지의 `SUBSCRIBE`, 현재 연결이 만든 구독의 `UNSUBSCRIBE`, 정상 `DISCONNECT`만 허용합니다. 클라이언트의 애플리케이션 `SEND`·`MESSAGE`는 모두 거부합니다.
- 크리처 홈에는 현재 접속한 그룹 구성원의 장착 상태가 반영된 아바타를 최대 20명까지 표시합니다.
- 사용자가 다른 아바타를 선택하면 닉네임, 시즌 기여도·그룹 내 순위와 장착 아이템을 확인하고 판매 중인 동일 상품의 상점 화면으로 이동할 수 있습니다.
- 서버는 접속·퇴장·장착 변경만 전파하고 아바타 이동 좌표는 지속적으로 송수신하지 않습니다.
- 접속 상태는 영구 업무 데이터로 저장하지 않으며 MVP는 단일 애플리케이션 인스턴스의 메모리 Presence를 사용합니다.

### 4.5. 결제와 환불

- 결제 연동 공급자는 포트원 V2 테스트 환경을 사용하고 PG 채널은 카카오페이 하나만 지원합니다.
- 브라우저 결제 요청은 `payMethod=EASY_PAY`, `currency=KRW`로 고정하며 다른 카드·계좌이체·가상계좌·휴대폰 결제 채널은 MVP 범위에서 제공하지 않습니다.
- 애플리케이션 결제 업무는 공급자 중립 `PaymentGateway` Port 뒤에 두고 포트원 SDK·REST·Webhook 형식은 Adapter에서 변환합니다.
- 아바타 꾸미기 아이템을 PG 테스트 결제로 구매할 수 있습니다.
- 결제 한 건당 아바타 꾸미기 아이템 하나를 구매합니다.
- 단순 구매만으로 아이템을 사용한 것으로 처리하지 않고 아바타에 처음 장착한 시각을 사용 시점으로 기록합니다.
- 한번 사용한 아이템은 장착을 해제해도 미사용 상태로 돌아가지 않습니다.
- 미사용 아이템은 환불할 수 있고, 사용한 아이템은 환불할 수 없습니다.
- 사용자는 구매 내역에서 환불을 요청하고 전체 관리자가 승인하거나 거절합니다.
- 승인 시 서버가 미사용·중복 환불 여부를 다시 검증한 뒤 PG 취소를 요청합니다.
- PG 취소에 성공하면 아이템을 회수하고 환불 완료로 처리합니다. 실패하면 결제와 아이템 소유 상태를 유지합니다.
- 포트원 취소 응답은 `SUCCEEDED → COMPLETED`, `FAILED → FAILED`, `REQUESTED → CANCEL_PENDING`으로 변환합니다. `REQUESTED`는 완료로 간주하지 않고 Webhook 또는 재조회로 확정합니다.
- PG Timeout이나 통신 단절로 취소 성공 여부를 알 수 없으면 `CANCEL_UNKNOWN`으로 기록하고, 아이템 장착과 중복 취소 요청을 차단한 채 PG 조회 API로 결과를 확인합니다.
- PG 취소 성공이 확인된 뒤에만 결제를 취소 완료로 변경하고 아이템을 회수합니다.
- `CANCEL_PENDING`이 5분 이상 지속되면 5분 주기 복구 작업이 PortOne 상태를 먼저 조회한 뒤 기존 멱등 키로 안전하게 완료·재시도·실패·결과 불명 상태를 확정합니다.
- Webhook의 `FAILED`와 5분 이상 지속된 `PENDING`은 5분 주기 결제 복구 작업이 PortOne 최신 상태를 조회하고 동일한 결제 정합성 Service로 재처리합니다.
- 결제 성공 여부, 아이템 보유·사용 여부와 환불 요청·처리 결과를 서버에서 관리합니다.
- 장착과 환불 승인, 중복 환불 승인 사이의 경합은 같은 구매·보유 아이템을 기준으로 잠금과 멱등 처리를 적용합니다.

### 4.6. 관리자와 사용자 환경

- 관리자는 회원, 그룹, 퀘스트, 랭킹, 결제와 환불 현황을 대시보드에서 확인할 수 있습니다.
- 사용자는 라이트 모드와 다크 모드를 전환할 수 있습니다.
- 라이트 테마는 메인 `#16836F`, 보조 `#A8DBC1`, 강조 `#FFD17B`, 배경 `#F3FAF6`를 사용하고 자연·성장·편안함을 시각 방향으로 삼습니다.
- 데스크톱은 좌측 사이드바, 모바일은 하단 5개 내비게이션을 사용하며 전체 관리자 화면은 별도 관리 사이드바를 제공합니다.

## 7. 개발 제약

- 개발 인원은 4명, 개발 기간은 약 2주입니다.
- 사용자에게 표시하는 서비스명은 `다 같이 키우는 생명체`이며 `공동 육성 게임`은 서비스 유형 설명으로 사용합니다.
- Group은 `com.team`, Artifact와 Name은 `shared-creature-game`, Package name은 `com.team.sharedcreature`를 사용합니다.
- 백엔드의 로컬 개발, Gradle Toolchain과 CI 실행 기준은 Java 21 LTS로 통일합니다.
- Spring Boot와 MySQL을 사용하고 웹 브라우저를 기본 클라이언트로 제공합니다.
- 서버 간 요청, PG 테스트 결제, 환불, WebSocket, 관리자 대시보드와 동시성 제어를 시연할 수 있어야 합니다.
- 최소 LLM 연동으로 새 그룹 소개 작성 중 Gemini에 최대 500자의 한국어 문장 교정을 요청하고, 사용자가 제안을 선택적으로 적용할 수 있어야 합니다.
- 업무 데이터를 표현하는 전체 테이블 수는 설계 결과 기준 30~40개를 목표로 합니다. 의미 없는 테이블 분할로 수를 맞추지 않고 각 테이블의 업무 책임과 관계를 설명할 수 있어야 합니다.
- 프로젝트 기간의 업무 테이블은 `photo_submissions`를 포함한 40개로 구현합니다. Spring Session과 스키마 이력 테이블은 인프라 테이블로 집계에서 제외합니다.
- 사용자·관리자 알림 기능과 `notifications` 테이블은 추후 구현 범위로 두고, 프로젝트 기간의 운영 이상은 관리자 대시보드 경고 목록으로 제공합니다.
- OAuth 로그인 시도는 10분 동안 유효하고 `CONSUMED`, `EXPIRED`, `FAILED` 종료 상태 전환 후 24시간이 지나면 물리 삭제합니다. 이는 계정·서버 세션 삭제와 무관합니다.
- OAuth 시작은 세션당 10분에 5회·IP당 10분에 30회, Gemini 교정은 사용자당 1분에 5회·`Asia/Seoul` 날짜당 30회로 제한합니다. Gemini 전체 동시 호출은 2건입니다.
- 평상시 개발은 localhost HTTP를 사용하고 `local` Profile에서만 세션 쿠키 `Secure=false`를 허용합니다. 모바일·OAuth·포트원 Redirect·Webhook 통합 검증에는 제품을 고정하지 않은 임시 HTTPS 터널과 `integration` Profile을 사용합니다.
- 위치정보와 인증정보 등 민감한 데이터는 목적에 필요한 범위에서만 다루고 사용자 화면이나 로그에 노출하지 않습니다.
- DB 시각은 UTC `DATETIME(6)`으로 저장하고 일일·주간·시즌 업무 경계는 `Asia/Seoul`로 계산합니다.
- 회원, 활동·보상 원장, 랭킹과 결제·환불 이력은 상태로 보존하며 프로젝트 범위에서 자동 삭제하지 않습니다.
- Scheduler 성공 기록은 90일, 실패 기록과 관리자 감사 로그는 1년 보관 후 배치 삭제합니다.
- 관리자 대시보드 운영 경고는 별도 알림 테이블 없이 Scheduler 실패, 퀘스트 배정 실패, 결과 불명 결제·환불, 그룹 인원 정합성 오류와 사진 삭제 실패의 현재 미해결 원본 상태만 조회합니다. 원본 상태가 정상화되면 목록에서 제외합니다.
- 공급자 토큰과 Secret은 저장하지 않고 PG 응답도 정합성 복구에 필요한 최소 필드만 저장합니다.
- 활성 그룹 소속, 진행 중 환불과 활성 초대 링크는 MySQL 생성 컬럼 UNIQUE 제약으로 이력을 보존하면서 현재 행의 유일성을 강제합니다.
- 그룹 정원은 `current_member_count` 조건부 갱신과 멤버십 생성을 같은 트랜잭션으로 처리해 20명을 초과하지 않게 합니다.
- 핵심 업무 FK는 `ON DELETE RESTRICT`를 기본으로 하며 회원·그룹·시즌·퀘스트·결제 이력에 Cascade 삭제를 사용하지 않습니다.
- 그룹당 활성 주 관리자 멤버십은 상태·역할 조건 생성 컬럼 UNIQUE 제약으로 한 명만 허용합니다.
- 초보 개발자는 [구현 시작 안내서](implementation-guide.md)의 순서대로 요청 ID, 화면, Operation ID, DTO, Service와 테이블을 추적합니다. 구현 중 문서에 없는 필드·상태·API를 임의로 추가하지 않고 설계 누락으로 기록해 먼저 합의합니다.
- REST API는 모든 Operation의 성공 HTTP 상태, 공통·업무 오류, 입력 위치, 요청·응답 필드의 타입·필수 여부·제한과 고정 정렬을 [REST API 설계서](api-design.md)에 정의합니다. 백엔드와 프론트엔드는 동일한 Operation ID와 DTO 필드명을 사용합니다.

## 8. MVP 완료 기준

다음 시나리오와 검증 결과를 통합 시연할 수 있으면 MVP가 완료된 것으로 판단합니다.

1. 사용자가 구글 또는 네이버 소셜 로그인으로 가입하거나 로그인합니다.
2. 사용자가 공개 그룹에 참여하고 그룹 크리처, 자신의 아바타와 퀘스트를 확인합니다.
3. 사용자가 일일·주간 퀘스트를 완료하면 서버가 조건을 판정하고 보상, 개인 기여도와 크리처 경험치를 반영합니다.
4. 동일 퀘스트의 중복 요청과 여러 사용자의 동시 완료 상황에서도 보상과 경험치 데이터의 정합성이 유지됩니다.
5. 확정된 성장·기여도·그룹 상태가 WebSocket을 통해 관련 사용자에게 갱신됩니다.
6. 사용자가 그룹 내 개인 랭킹과 그룹 간 랭킹을 확인합니다.
7. 사용자가 아바타 꾸미기 아이템을 PG 테스트 결제로 구매합니다.
8. 미사용 아이템의 환불은 승인되고 사용한 아이템의 환불은 거절됩니다.
9. 관리자가 회원, 그룹, 퀘스트, 랭킹, 결제와 환불 현황을 대시보드에서 확인합니다.
10. 사용자가 라이트 모드와 다크 모드를 전환하고 주요 화면을 두 모드에서 사용할 수 있습니다.
11. 데이터베이스 설계가 30~40개의 업무 테이블과 핵심 관계를 포함하고, 구현된 핵심 흐름이 해당 설계와 일치합니다.
12. 사용자가 그룹 소개 문장을 Gemini로 교정해 제안을 확인하고 선택적으로 적용하며, Gemini 장애 시에도 원문으로 그룹을 생성할 수 있습니다.
13. 사용자가 Android Chrome과 iOS Safari에서 위치·촬영 시각 EXIF가 포함된 JPEG 사진을 제출하고 서버가 유효·무효를 판정하며, GPS가 없거나 JPEG가 아닌 사진은 보상 없이 실패합니다.
14. 다른 브라우저의 OAuth Callback, 허용하지 않은 WebSocket `SEND`·구독과 다른 사용자의 구매·환불 자원 접근이 서버에서 차단됩니다.
15. 임시 공개 HTTPS 주소에서 모바일 OAuth·결제 Redirect와 포트원 Webhook 수신을 통합 검증합니다.

EXIF 제출은 1시간을 넘긴 미처리 건을 실패로 전환합니다. 실패 파일과 좌표는 판정 후 24시간 이내, 성공 파일과 좌표는 시즌 종료 후 30일에 삭제하되 판정 결과와 최소 활동 이력은 유지합니다.
