# 다 같이 키우는 생명체

> 팀 프로젝트 통합 기획서 **v0.2** · 2026-11-02 기획 합의 반영  
> **서비스명:** 다 같이 키우는 생명체
> **서비스 유형:** 공동 육성 게임
> **개발 조건:** 4명 · 약 2주 · Java 21 LTS · Spring Boot · MySQL · 웹 브라우저 중심
> **문서 단계:** 서비스 기획 / MVP 범위 정의 (상세 설계 이전)

## 1. 프로젝트 개요

**한 줄 소개:** 누구나 참여할 수 있는 그룹에서 일상 퀘스트와 야외 미션을 수행하고, 공동 크리처를 성장시키며 개인·그룹 간에 경쟁하는 웹 기반 소셜 육성 서비스.

가입한 사용자는 그룹에 참여해 일일·주간 퀘스트를 수행한다. 퀘스트 성과는 크리처의 성장과 개인 기여도에 반영되며, 그룹 내 개인 랭킹 및 그룹 간 랭킹을 통해 협력과 경쟁의 동기를 함께 제공한다.

게임에서 다루는 대상을 **크리처(육성 대상)**와 **아바타(사용자 꾸미기 대상)**로 분리한다. 크리처의 육성·성장은 게임 플레이의 요소이며, 결제 기능은 아바타를 꾸미는 상품에 연결한다. 기본 서비스는 별도의 모바일 앱 설치 없이 웹 브라우저로 접근할 수 있도록 기획한다.

## 2. 기획 배경과 해결하려는 문제

- **일상 활동의 동기 부족:** 실내에서 즐기는 활동이 많아지면서 일부 사용자는 가벼운 외출이나 규칙적인 생활을 시작할 계기를 얻기 어렵다.
- **사회적 교류의 진입 장벽:** 새로운 사람들과 대화를 시작하거나 적극적인 SNS 활동을 이어가는 것을 부담스럽게 느낄 수 있다.
- **활동 지속의 어려움:** 산책·기상 습관처럼 작지만 꾸준한 활동은 혼자 지속할 동기가 약할 수 있다.

**해결 방향:** 가벼운 퀘스트를 게임의 성장·경쟁 요소에 연결하고, 낯선 사용자와도 하나의 목표를 공유하며 느슨하게 협력할 수 있는 참여 경험을 제공한다. 개인의 활동은 크리처 육성에, 여러 사람의 활동은 그룹 성과에 반영한다.

> 사회적 고립 감소, 야외 활동 증가, 생활 습관 개선은 서비스가 지향하는 **가설적 기대 효과**이며, 현재 검증된 결과로 제시하지 않는다.

## 3. 주요 사용자와 서비스 콘셉트

- **주요 대상:** 작은 일상 활동에 동기가 필요한 사람, 가벼운 게임을 즐기는 사람, 다른 사용자와 공동 목표를 공유하고 싶은 사람.
- **참여 범위:** **가입 사용자 전체**를 대상으로 한다. 친구·지인 초대에 제한되는 프라이빗 서비스로 기획하지 않는다.
- **그룹:** 공개적인 참여를 전제로 여러 사용자가 소속되고, 그룹 단위의 크리처 육성 및 경쟁이 이루어진다.
- **크리처:** 퀘스트 성과로 성장·진화하는 **육성 요소**. 유료 구매를 성장 조건에 포함하지 않는다.
- **아바타:** 사용자에게 연결되는 **꾸미기 요소**. 외형을 바꾸는 상품을 테스트 결제 대상으로 삼는다.
- **경쟁:** **그룹 내 개인 기여도**와 **그룹 간 경쟁**을 모두 제공한다.
- **게임 표현:** 웹 기반 이미지·간단한 애니메이션으로 성장과 꾸미기 결과를 표현한다.

**육성 단위:** 그룹마다 시즌별 활성 공동 크리처 1마리를 육성하며 개인별 크리처는 MVP에 포함하지 않는다. 크리처는 공동 육성, 사용자 아바타는 꾸미기 과금 역할을 담당한다.

**참여 방식:** 그룹 없는 사용자가 정원이 남은 공개 그룹을 직접 선택해 승인 없이 가입하거나 새 그룹을 생성한다. 자동 매칭과 추천 배정은 제공하지 않는다.

## 4. 핵심 이용 흐름

1. 사용자가 구글 또는 네이버 소셜 로그인으로 가입한다.
2. 가입 사용자가 정원이 남은 공개 그룹을 선택해 가입하거나 새 그룹을 생성한다.
3. 그룹의 크리처와 본인의 아바타, 오늘의 퀘스트를 확인한다.
4. 일일·주간 퀘스트를 수행하고 결과를 제출한다.
5. 서버가 퀘스트 조건을 검사해 보상을 지급하고, 개인 기여도와 그룹 성장 상태를 갱신한다.
6. 관련 사용자에게 성장 및 기여도 변화가 실시간 반영된다.
7. 개인·그룹 랭킹을 통해 경쟁 결과를 확인한다.
8. 원하는 사용자는 **아바타 꾸미기 아이템**을 PG 테스트 결제로 구매한다. 사용 여부에 따라 환불 가능 여부를 판정한다.

## 6. 퀘스트 시스템과 야외 사진 인증

### 6.1 퀘스트 구성

야외 활동은 **여러 일일·주간 퀘스트 중 하나**이며, 크리처를 성장시키기 위한 유일한 경로가 아니다.

| 분류 | 퀘스트 예시 | 판정 개념 |
|---|---|---|
| 일일 | **기상 미션** | 지정 시간 조건 내 웹 체크인 |
| 일일 | 오늘의 위치 사진 | 당일 촬영한 GPS 포함 JPEG 1건 |
| 주간 | 주간 위치 기록 | 서로 다른 KST 날짜 2일에 유효 사진 제출 |
| 주간 | 주간 탐험 | 해당 주에 유효한 장소 인증 실적 누적 |
| 일일·주간 | 기타 생활 미션 | 자기 확인, 서비스 체크인과 서버 집계로 판정하는 확정 템플릿 |

**기상 미션의 기술적 의미:** `Asia/Seoul` 기준 05:00 이상 09:00 미만에 사용자가 명시적으로 실행한 서비스 체크인을 오전 기상 체크인으로 분류합니다. 실제 잠에서 깨어난 시각은 검증하지 않고 사용자별 시간 변경과 지각 인정은 제공하지 않습니다.

### 6.2 사진 EXIF 기반 인증 구상

1. 사용자가 촬영한 사진을 웹사이트에 업로드한다.
2. Spring Boot 서버가 이미지에서 **GPS 위치와 촬영 시각**을 추출한다.
3. 해당 퀘스트의 위치·날짜·중복 제출 조건을 검사한다.
4. 유효한 인증에 한해 퀘스트 완료 및 보상을 반영한다.

**확정된 실패 정책:** **GPS 정보가 없는 사진은 예외 없이 위치 인증 실패**로 처리한다. 메타데이터가 없는 사진에 대한 대체 인증, 별도 보상이나 예외 인정 정책의 개발은 **프로젝트 이후 과제**로 둔다. MVP에는 유효하지 않은 제출을 거절하는 기본 처리만 둔다. 다른 종류의 퀘스트를 수행할 수 있다는 점과, 해당 사진의 인증을 예외적으로 승인한다는 점은 구분한다.

**중요한 한계:** GPS와 촬영 시각은 삭제·변조가 가능하다. MVP는 GPS 존재·좌표 범위와 촬영 시각의 배정 기간 포함 여부만 확인하며 실외 촬영, 현재 위치, 특정 장소·반경, 사진 간 거리와 실제 이동을 증명하지 않는다.

**필수 기술 검증:** Android Chrome과 iOS Safari에서 촬영한 JPEG 파일을 브라우저로 업로드했을 때 EXIF GPS·촬영 시각이 유지되고 서버가 이를 추출하는지 확인한다. 검증 실패는 기능 제외가 아니라 MVP 미완료로 처리한다. 최대 10 MiB의 JPEG만 지원하고 HEIC·HEIF는 명확한 오류로 거절한다.

**개인정보 보호:** 원본 GPS 좌표를 다른 사용자나 그룹 랭킹에 공개하지 않는다. 실패 파일·좌표는 판정 후 24시간 이내, 성공 파일·좌표는 시즌 종료 후 30일에 삭제한다.

## 8. 아이템·결제·환불 및 수익 모델

### 8.1 이번 프로젝트에서 구현할 과금

- **판매 대상:** 사용자 **아바타 꾸미기 아이템**.
- **비과금 대상:** **크리처의 기본 육성·성장 과정**. 현 단계에서는 과금 기능과 연결하지 않는다.
- **결제 방식:** PG 연동 **테스트 결제**.
- **환불 기준:** **구매 아이템이 미사용이면 환불 가능, 사용한 아이템은 환불 불가**를 기본 정책으로 한다.
- **필요한 상태 관리:** 결제 성공 여부, 아이템 보유 여부, 사용 여부, 환불 요청 및 결과.

**사용 시점:** 꾸미기 아이템은 아바타에 최초 장착한 순간 사용으로 확정합니다. 단순 구매만으로 사용 처리하지 않으며 장착을 해제해도 미사용 상태로 돌아가지 않습니다.

### 8.2 향후 검토

광고 시청 보상, 광고 제거, 편의성 아이템 등은 팀원이 제안한 확장 가능성으로 남긴다. **실제 광고 연동이나 유료 성장 버프는 이번 2주 MVP 범위에 포함하지 않는다.**

## 9. 개발 범위 및 2주 추진 방향

**MVP 필수 범위:** 계정 인증, 전체 가입자 대상 그룹 참여, 그룹 크리처 육성, 사용자 아바타, 일일·주간 퀘스트, 보상·기여도, **그룹 내 개인 랭킹·그룹 간 랭킹**, WebSocket 상태 갱신, 동시성 방지, 아바타 꾸미기 아이템 테스트 결제·환불, 관리자 대시보드, 다크 모드.

**필수 기술 검증 범위:** 사진 EXIF 기반 위치 인증 퀘스트는 핵심 기능이므로 Android Chrome과 iOS Safari의 촬영·업로드·서버 판정 흐름을 MVP 완료 전에 통과해야 한다.

**프로젝트 이후 과제:** GPS 없는 사진의 대체 인증·예외 인정 정책, 복잡한 부정행위 탐지, 광고 시스템, 모바일 네이티브 연동, 정밀 GPS 경로 추적, 복잡한 소셜 기능.

| 단계 | 중점 목표 |
|---|---|
| 1~2일차 | 크리처/아바타 역할·그룹 참여·랭킹 규칙 확정, 화면·데이터 초안, EXIF 기술 검증 |
| 3~5일차 | 계정·그룹·육성·아바타·일일 퀘스트 기본 구현 |
| 6~9일차 | 일일·주간 퀘스트, WebSocket, 랭킹·동시성, 테스트 결제·환불 병렬 개발 |
| 10~12일차 | 사진 인증 가능 범위 반영, 관리자 기능, 통합 테스트 |
| 13~14일차 | 경합/중복 요청·결제·환불 시나리오 테스트, 시연 및 발표 준비 |

**4인 역할 분담 예시:** ① 계정·그룹 ② 크리처·퀘스트·동시성 ③ 프론트엔드·아바타·실시간 경험 ④ 결제·환불·관리자. 그룹·개인 랭킹의 데이터 산출은 크리처·퀘스트와 연계해 분담한다. 최종 분담은 팀원 합의로 결정한다.

## 10. 성과 확인 지표

- 전체 가입자 중 퀘스트 참여 사용자 비율
- 그룹당 주간 참여 사용자 수와 퀘스트 완료 수
- 개인 기여도 및 그룹 간 점수 집계의 정확성
- 크리처 성장·진화 단계별 도달 현황
- 동시 완료·중복 제출 시 보상 데이터 정합성
- 위치 메타데이터가 유효한 사진의 인증 성공 여부
- 테스트 결제·아이템 사용·환불 조건 분기 처리 성공 여부

> 위 지표는 구현 상태와 참여 현황을 확인하기 위한 것이며, 사회적 고립이나 신체 활동의 개선 효과를 입증한 것은 아니다.

## 11. 합의 완료 사항 및 구현 검증 항목

### 이번 논의에서 확정한 사항

1. **육성·과금 대상 분리:** 크리처는 육성 요소, 아바타는 꾸미기 과금 요소. 크리처의 육성은 현재 과금과 무관하다.
2. **대상 사용자:** 친구 초대형으로 제한하지 않고 **가입 사용자 전체**에게 참여를 개방한다.
3. **퀘스트 구성:** 야외 위치 인증은 여러 **일일·주간 퀘스트 중 하나**이며, **기상 미션**도 퀘스트 후보에 포함한다.
4. **GPS 없는 사진:** 예외 없이 인증 실패. 대체 인증과 별도 예외 정책은 **프로젝트 이후 과제**로 둔다.
5. **상품·환불:** **아바타 꾸미기 아이템**을 테스트 결제 대상으로 하고, **사용 여부**로 환불을 판단한다.
6. **경쟁:** **그룹 내 개인 기여도 랭킹** 및 **그룹 간 경쟁**을 모두 도입한다.
7. **그룹·크리처 단위:** 공개 그룹마다 활성 크리처 1마리를 육성하며 개인별 크리처는 MVP에서 제외한다. 그룹 최초 생성자는 해당 그룹의 주 관리자가 된다.
8. **그룹 가입과 정원:** 사용자는 동시에 하나의 그룹에만 소속되며, 정원이 남은 공개 그룹을 직접 선택해 승인 없이 가입한다. 그룹당 정원은 20명으로 제한한다.
9. **관리자 통계 시각화:** 관리자 대시보드 차트에는 Google Charts JavaScript 라이브러리를 사용한다.
10. **그룹 탈퇴와 재가입:** 탈퇴 시각부터 24시간이 지나기 전에는 어떤 그룹에도 가입할 수 없고, 기존 그룹에 반영된 크리처 경험치와 그룹 점수는 유지하며 새 그룹으로 이전하지 않는다.
11. **그룹 가입 링크:** 그룹 생성 시 소셜 회원가입과 그룹 가입을 함께 처리하는 사용 횟수 무제한 링크를 자동 생성한다. 미가입자가 수락하고 구글 또는 네이버 인증을 완료하면 계정 생성과 그룹 가입을 함께 완료하며, 거절하면 계정을 생성하지 않은 채 일반 소셜 로그인·회원가입 화면으로 이동한다. 링크는 정원을 예약하지 않으며 수락 시 정원, 기존 소속과 탈퇴 후 24시간 제한을 다시 검사한다.
12. **탈퇴 회원 기록:** 개인의 퀘스트·기여 이력은 보존하고 진행 중인 그룹 개인 랭킹에는 `탈퇴` 상태로 유지한다. 탈퇴 후 추가 기여는 중단하고 현재 그룹 구성원 목록에서는 제외한다.
13. **사용자 역할:** 전체 관리자는 여러 그룹을 관리한다. 그룹 최초 생성자는 그룹당 1명인 주 관리자가 되고, 주 관리자는 같은 그룹의 일반 사용자에게 부 관리자 권한을 부여하거나 회수할 수 있다. 부 관리자는 복수로 둘 수 있으며 일반 사용자 관리 권한은 갖지만 관리자 권한을 부여하거나 회수하지 못한다. 일반 사용자는 하나의 그룹에만 소속된다.
14. **탈퇴와 강퇴:** 일반 사용자는 직접 탈퇴할 수 있다. 전체 관리자는 신고를 근거로 사용자를 강퇴할 수 있고, 미접속 강퇴 기준은 마지막 인증 활동 후 3일 이상이다. 로그인 성공과 인증 API 요청 성공을 활동으로 보며 활동 시각은 최대 10분 간격으로 저장한다. 주 관리자는 대체자를 지정하기 전까지 권한 해제나 자진 탈퇴가 불가능하며 전체 관리자가 주 관리자를 재지정할 수 있다. 자진 탈퇴와 모든 강퇴에는 동일한 24시간 가입 제한을 적용한다.
15. **회원가입·그룹 선택 화면:** 일반 회원가입을 완료하면 별도 그룹 선택 페이지로 이동한다. 그룹 선택 페이지는 신규 가입자와 탈퇴·강퇴 후 24시간 제한이 끝난 사용자가 공통으로 사용한다.
16. **가입 링크 수명:** 자동 생성 링크는 만료되지 않고 사용 횟수 제한이 없다. 재발급하면 기존 링크는 즉시 무효화된다.
17. **그룹 관리자 강퇴 범위:** 부 관리자는 마지막 인증 활동 후 72시간이 지난 일반 회원만 강퇴할 수 있고 주 관리자나 다른 부 관리자를 강퇴할 수 없다. 주 관리자는 일반·부 관리자 회원 모두 마지막 인증 활동 후 72시간이 지나야 강퇴할 수 있으며 부 관리자 권한 회수에는 활동 조건을 적용하지 않는다.
18. **그룹 선택과 생성:** 그룹이 없는 사용자는 그룹 선택 페이지에서 기존 공개 그룹에 가입하거나 새 그룹을 생성할 수 있다. 새 그룹 생성자는 주 관리자가 된다.
19. **초대 링크 흐름과 권한:** 수락하면 링크 정보를 유지한 소셜 로그인·회원가입 화면으로 이동하고 OAuth 완료와 동시에 해당 그룹에 가입한다. 거절하면 링크 정보를 버리고 일반 소셜 로그인·회원가입 화면으로 이동한다. 링크 재발급은 주 관리자만 할 수 있다.
20. **공동 크리처 시즌:** 서비스 공개와 첫 시즌을 `Asia/Seoul` 기준 같은 월요일 0시에 시작하고 이후 4주마다 크리처를 교체한다. 기존 그룹은 시즌 시작, 시즌 중 생성된 그룹은 생성 시각부터 3일간 알 상태이며 주·부 관리자가 선택을 변경할 수 있다. 그룹별 72시간 시점에 최종 선택 크리처로 부화하고 선택이 없으면 무작위 부화한다. 공개 전 배포·점검은 가능하지만 별도 프리시즌 기능은 제공하지 않는다.
21. **퀘스트 갱신:** `Asia/Seoul` 기준 일일 퀘스트는 매일 0시, 주간 퀘스트는 매주 월요일 0시에 갱신한다.
22. **시즌 전환 데이터:** 종료된 크리처 최종 상태와 시즌 랭킹은 보존한다. 새 시즌에는 크리처 경험치, 시즌 기여도와 시즌 그룹 점수를 초기화하고 회원, 그룹, 아이템과 누적 활동 기록은 유지한다.
23. **초대 링크 가입 실패:** OAuth 콜백은 신규 계정을 만들지 않고 검증된 소셜 정보와 초대 문맥을 가입 대기 세션에 저장한다. `/signup`에서 닉네임을 제출해 계정을 생성하기 직전에 링크와 그룹 가입 조건을 다시 검사한다. 조건을 충족하지 못하면 계정은 생성하되 그룹에는 가입시키지 않고, 실패 이유를 표시한 뒤 그룹 선택 페이지로 이동한다. 기존 가입자는 새 계정을 만들지 않으며 그룹이 없고 조건을 충족하면 수락 즉시 초대 그룹에 가입한다.
24. **크리처 성장 단계:** `알 → 유년기 → 성장기 → 성숙기 → 완전체` 순서로 성장한다. 부화 후 그룹 누적 경험치 45,000, 97,500, 150,000에서 성장기, 성숙기, 완전체로 진화한다.
25. **경험치 획득과 누적:** 서버가 유효하게 판정한 일일·주간 퀘스트만 크리처 경험치를 지급한다. 퀘스트별 크리처 경험치와 개인 기여도 점수를 분리하고, 경험치는 완전체 기준을 넘어서도 제한 없이 누적한다.
26. **시즌 랭킹 점수:** 개인 기여도는 퀘스트별 기여도 점수의 시즌 합계, 그룹 점수는 소속 사용자들의 시즌 기여도 합계로 계산한다. 결제 금액과 아이템 구매는 반영하지 않는다.
27. **랭킹 초기화·보존과 동점:** 새 시즌에 개인·그룹 점수를 0으로 초기화하고 종료된 시즌 랭킹은 조회 가능하게 보존한다. 동점은 해당 점수에 먼저 도달한 대상을 우선하고 도달 시각도 같으면 ID 오름차순으로 정한다.
28. **퀘스트 순회 배정:** 시스템이 개발자가 정의한 순회 규칙에 따라 일일 3개와 주간 7개를 선정해 모든 사용자에게 동일하게 배정한다. 관리자는 목록을 수동 선택하지 않으며 각 퀘스트는 기간당 한 번만 완료할 수 있고 이월하지 않는다.
29. **퀘스트 경험치:** 일일 퀘스트는 100, 주간 퀘스트는 300의 크리처 경험치를 지급한다. 사용자 1명의 주간 최대 경험치는 4,200이며 퀘스트에는 난이도 상·중·하 배점이 있다.
30. **알 상태 경험치:** 그룹의 시즌 참여 첫 3일에도 경험치와 기여도를 누적하고 부화 시 누적 경험치를 적용해 도달한 성장 단계로 즉시 전환한다.
31. **난이도 기여도:** 난이도는 크리처 경험치에 영향을 주지 않고 개인 기여도에만 반영한다. 일일 퀘스트는 하 10·중 20·상 30, 주간 퀘스트는 하 30·중 60·상 90을 지급한다.
32. **난이도 구성과 중복:** 일일은 하·중·상 각 1개, 주간은 하 3개·중 2개·상 2개로 구성하며 같은 기간에는 동일 템플릿을 중복 배정하지 않는다. 다음 기간에는 순회 규칙에 따라 다시 배정할 수 있다.
33. **템플릿 부족:** 필요한 난이도별 템플릿이 부족하면 배정 생성을 실패 처리하고 관리자 대시보드 경고 목록에 부족한 난이도와 개수를 표시한다. 개발자가 순회 구성을 보완한 뒤 다시 생성한다.
34. **아이템 사용 시점:** 결제 한 건당 아바타 아이템 하나를 구매하며 최초 장착 시 사용으로 확정한다. 장착을 해제해도 미사용 상태로 돌아가지 않는다.
35. **환불 흐름:** 사용자가 환불을 요청하고 전체 관리자가 승인·거절한다. 승인 시 미사용과 중복 환불 여부를 재검사하고 PG 취소 성공 후 아이템을 회수한다.
36. **핵심 동시성 제어:** 퀘스트 완료·보상에는 UNIQUE 제약과 그룹 상태 잠금을, 그룹 가입에는 사용자·그룹 잠금을, 장착·환불에는 구매·보유 아이템·환불 요청 잠금을 적용한다. 스케줄 실행은 기간별 UNIQUE 제약으로 멱등 처리한다.
37. **PG 취소 경계:** 짧은 트랜잭션에서 `CANCEL_PENDING`을 선점하고 Commit 후 멱등 키로 PG를 호출한 뒤 별도 트랜잭션에서 성공·실패를 확정한다.
38. **인증 공급자:** 회원가입과 로그인은 구글·네이버 소셜 로그인만 지원하며 자체 비밀번호는 저장하지 않는다.
39. **클라이언트 구조:** 화면은 Full CSR로 구성하고 Spring Boot는 REST API와 OAuth 콜백을 제공한다.
40. **계정 연결:** 소셜 계정은 공급자와 공급자 사용자 식별자로 구분한다. 동일 이메일의 다른 공급자 계정은 자동 연결하지 않고 기존 가입 공급자로 로그인하도록 안내한다.
41. **인증 방식:** OAuth Authorization Code는 백엔드가 교환하고 애플리케이션 인증은 Spring Session JDBC 기반 서버 세션으로 유지한다. 공급자 토큰은 브라우저에 전달하거나 영구 저장하지 않는다.
42. **세션·이메일 정책:** 세션은 7일 비활성 만료, 사용자당 최대 3개로 제한하고 초과 시 가장 오래된 세션을 종료한다. 신규 가입은 공급자 이메일이 필수이며 기존 회원은 공급자 식별자가 일치하면 이메일 누락 상태에서도 로그인한다.
43. **네이버 검수 범위:** 개발·시연 단계에서는 팀원 4명을 관리자·테스터로 등록해 사용한다. 모든 네이버 사용자가 로그인하는 공개 운영 전에는 네이버 사전 검수를 통과해야 한다.
44. **결제·환불 상태머신:** 결제는 `READY → PAID/FAILED`, 환불은 `REQUESTED → REJECTED` 또는 `CANCEL_PENDING → COMPLETED/FAILED/CANCEL_UNKNOWN`으로 관리한다. `CANCEL_UNKNOWN`은 PG 조회 결과로만 후속 상태를 결정한다.
45. **결과 불명 보호:** `REQUESTED`, `CANCEL_PENDING`, `CANCEL_UNKNOWN` 동안 아이템 장착을 차단하고 환불 `COMPLETED`가 확정된 뒤에만 결제를 `CANCELLED`, 아이템을 `REVOKED`로 전환한다.
46. **퀘스트 카탈로그 규모:** 일일 템플릿은 하 5·중 4·상 3개, 주간 템플릿은 하 6·중 4·상 4개 이상을 활성 상태로 유지한다.
47. **결정적 순회:** 첫 시즌 시작부터의 KST 누적 일수·주차와 난이도별 오프셋 하 0·중 1·상 2를 사용해 원형 순회하며 시즌 전환 시 인덱스를 초기화하지 않는다.
48. **배정 Snapshot:** 템플릿 버전, 문구, 난이도, 검증 조건·파라미터, 경험치와 기여도를 배정에 복사하고 템플릿 변경은 다음 갱신부터 적용한다.
49. **퀘스트 검증 유형:** 생활 활동은 `SELF_CHECK`, 서비스 행동은 `SERVER_EVENT`, 주간 누적은 `AGGREGATE`, 위치 사진은 `PHOTO_EXIF`로 판정한다.
50. **완료 신뢰 경계:** 서버가 기간·자격·중복과 Snapshot 보상을 검증하며 클라이언트 누적값과 보상값을 신뢰하지 않는다. 관리자 수동 승인, 사후 증빙과 완료 취소는 MVP에서 제외한다.
51. **퀘스트 카탈로그:** 일일 13개와 주간 15개의 활성 템플릿을 생활 자기 확인, 명시적 서비스 체크인, 서버 집계와 EXIF 위치 사진으로 구성한다. 위치 사진 일일·주간 템플릿은 중 난이도로 순회한다.
52. **체크인 기준:** 서비스 체크인은 단순 페이지 조회가 아닌 사용자당 KST 날짜별 1회의 명시적 행동이며, 05:00 이상 09:00 미만 체크인을 오전 기상 체크인으로 분류한다.
53. **데이터베이스 규모:** 계정 4, 그룹 7, 시즌·크리처·랭킹 9, 퀘스트·활동 9, 결제·아바타 8, 운영 공통 3개로 총 40개 업무 테이블을 구현하며 필수 `photo_submissions`를 포함한다.
54. **인프라 테이블 제외:** Spring Session과 스키마 마이그레이션 테이블은 업무 테이블 수에 포함하지 않는다.
55. **DB 공통 형식:** 기본키는 `BIGINT AUTO_INCREMENT id`, 외래키는 `{대상}_id`, 상태는 `VARCHAR(30)`, 금액·경험치·점수는 `BIGINT`, 위·경도는 `DECIMAL(10, 7)`을 사용한다.
56. **시간·보존 정책:** 시각은 UTC `DATETIME(6)`으로 저장하고 업무 경계는 KST로 계산한다. 탈퇴·이력·원장·결제 데이터는 상태로 보존하고 모든 테이블에 공통 논리 삭제나 버전 컬럼을 강제하지 않는다.
57. **JSON·비밀정보:** JSON은 검증 파라미터와 비핵심 외부 응답에 한정하고 검색·제약·정산 값은 일반 컬럼으로 저장한다. 공급자 토큰과 Secret은 저장하지 않는다.
58. **활성 행 제약:** 활성 소속, 진행 중 환불과 활성 초대 링크는 상태 조건 STORED 생성 컬럼과 UNIQUE 인덱스로 한 건만 허용한다.
59. **그룹 정원 카운터:** `groups.current_member_count`를 조건부 증가한 뒤 같은 트랜잭션에서 멤버십을 생성한다. 탈퇴·강퇴도 멤버십 종료와 카운터 감소를 함께 처리한다.
60. **카운터 복구:** Scheduler는 활성 멤버십 수와 카운터 불일치를 감지해 관리자 대시보드 경고·감사 로그를 남기며 자동 수정하지 않는다.
61. **관계 Cardinality:** 소셜 계정·프로필은 사용자와 1:1, 그룹·시즌·퀘스트·결제 이력은 기준 Aggregate와 1:N으로 보존하며 업무별 활성 행만 UNIQUE로 제한한다.
62. **FK 삭제 정책:** 핵심 업무 FK는 `ON DELETE RESTRICT`를 사용하고 Cascade 삭제를 금지한다. 임시 OAuth 시도만 명시적으로 물리 삭제한다.
63. **주 관리자 제약:** `groups.primary_admin_user_id`를 유지하고 활성 PRIMARY 멤버십의 `primary_group_id` 생성 컬럼 UNIQUE로 그룹당 한 명을 보장한다.
64. **이름 식별 정책:** 닉네임은 전역 2~20자, 그룹 이름은 전역 2~30자로 중복을 금지하고 정규화 컬럼에 UNIQUE를 적용한다. 그룹 이름은 MVP에서 변경하지 않는다.
65. **인증 토큰 저장:** 소셜 이메일은 가입 당시 Snapshot으로 유지하고 OAuth state와 초대 링크 토큰은 SHA-256 Hash만 저장한다.
66. **계정·그룹 상세 명세:** 계정·인증 4개와 그룹·운영 7개 테이블의 컬럼, 상태, FK, 생성 컬럼과 조회 인덱스를 데이터베이스 설계서 기준으로 구현한다.
67. **시즌·크리처 상세 명세:** 시즌·크리처·랭킹 9개 테이블의 컬럼, 상태, UNIQUE와 조회 인덱스를 데이터베이스 설계서 기준으로 구현한다.
68. **알 경험치 저장:** `group_creatures`는 기존 그룹이면 시즌 시작 시, 시즌 중 새 그룹이면 그룹 생성 시 알 상태로 만들고 경험치를 즉시 누적한다. 부화 시 최종 종과 누적 경험치 기준 최고 성장 단계를 확정한다.
69. **랭킹 Snapshot:** 종료 랭킹에는 점수·도달 시각·탈퇴 상태와 닉네임·그룹 이름 Snapshot을 저장하고 생성 후 수정하지 않는다.
70. **퀘스트·활동 상세 명세:** 템플릿, 버전, 기간, 배정, 완료, 보상 원장, 활동 이벤트, 체크인과 사진 제출 9개 테이블의 컬럼·UNIQUE·인덱스를 데이터베이스 설계서 기준으로 구현한다.
71. **완료 그룹 귀속:** 완료 행에 당시 그룹 시즌과 멤버십을 저장하고 이후 탈퇴·이동에도 변경하지 않는다.
72. **활동 신뢰 경계:** 활동 이벤트는 서버만 생성하고 클라이언트 누적값을 신뢰하지 않는다. 사진 Binary와 원본 EXIF 전체는 DB에 저장하지 않는다.
73. **결제·아바타 상세 명세:** 상품, 주문, PG 거래, 보유 아이템, 장착, 환불, PG 시도와 Webhook 8개 테이블의 컬럼·상태·UNIQUE·인덱스를 데이터베이스 설계서 기준으로 구현한다.
74. **아바타 슬롯:** `HEAD`, `FACE`, `BODY`, `ACCESSORY` 네 슬롯을 사용하고 사용자·슬롯당 하나, 보유 아이템당 한 슬롯만 장착한다.
75. **결제 최소 저장:** 주문은 상품·가격·슬롯 Snapshot을 보존하고 PG 시도·Webhook은 원문 대신 멱등 키, 이벤트 ID, Payload Hash와 정제된 최소 필드만 저장한다.
76. **알림 범위:** 사용자·관리자 알림 기능과 `notifications` 테이블은 프로젝트 이후 구현한다. 프로젝트 기간에는 운영 이상을 관리자 대시보드 경고 목록으로 제공한다.
77. **OAuth 임시 상태 보존:** OAuth 로그인 시도는 10분 동안 유효하고 종료 상태 전환 후 24시간이 지나면 삭제한다. 계정·소셜 연결·로그인 세션에는 영향을 주지 않는다.
78. **운영 기록과 경고:** Scheduler 실행은 작업 종류·기준 시각 UNIQUE와 Lease로 중복 실행을 제어한다. 성공 기록은 90일, 실패 기록과 관리자 감사 로그는 1년 보관한다. 운영 경고는 별도 알림 테이블 없이 현재 미해결 원본 오류 상태만 관리자 대시보드에서 조회하고 정상화되면 목록에서 제외한다.
79. **EXIF 필수 구현과 보존:** Android Chrome과 iOS Safari 실기기에서 GPS·촬영 시각 추출과 판정 흐름을 필수 검증한다. 실패 파일·좌표는 판정 후 24시간 이내, 성공 파일·좌표는 시즌 종료 후 30일에 삭제하고 최소 판정 이력만 유지한다.
80. **CSR 경로와 접근 제어:** 공개, 가입, 그룹 회원, 그룹 관리자와 전체 관리자 화면을 URL로 분리한다. `/api/v1/me` 상태로 Route Guard를 적용하되 실제 권한은 서버 API가 재검증하고, 그룹 가입 제한 중에는 그룹 선택 화면에서 남은 시간을 표시한다.
81. **레이아웃과 색상:** 데스크톱은 좌측 사이드바, 모바일은 하단 5개 내비게이션을 사용한다. 자연·성장·편안함을 방향으로 메인 `#16836F`, 보조 `#A8DBC1`, 강조 `#FFD17B`, 라이트 배경 `#F3FAF6`를 적용하고 시스템·라이트·다크 테마를 제공한다.
82. **핵심 화면 상태:** 크리처 홈, 퀘스트, 랭킹과 그룹 화면에 필요한 시즌·경험치·기여·역할 정보를 표시한다. 조회에는 Skeleton·빈 상태·재시도를 제공하고 WebSocket 재연결 뒤 REST로 상태를 재동기화한다. Toast는 영속 알림이 아닌 현재 작업 결과에만 사용한다.
83. **관리자 대시보드:** 활동 사용자, 그룹 정원, 퀘스트 완료, 결제·환불, 신고와 운영 경고를 요약하고 Google Charts로 추이를 표시한다. KST 기간·그룹 필터를 제공하며 표시 중 60초 자동 갱신, 수동 갱신과 표 대체 정보를 지원한다.
84. **그룹 관리·결제 화면:** 그룹 관리 화면은 역할과 마지막 인증 활동에 따라 허용되는 강퇴·권한·초대·크리처 작업만 제공한다. 상점·아바타·결제 화면은 사용 처리와 환불 가능 여부, PG 결과 불명 상태를 명확히 표시하고 모든 조건을 제출 시 재검증한다.
85. **가입·그룹 선택 입력:** 회원가입은 소셜 정보 확인과 닉네임 입력만 제공하고, 그룹 선택은 검색·페이지 조회·그룹 생성을 지원한다. 이름·정원·소속·재가입 제한·초대 링크는 제출 시 서버가 최종 검사하며 업무 실패 이유를 구체적으로 표시한다.
86. **공통 REST 계약:** `/api/v1` 아래에서 `data`·`meta` 성공 응답과 코드 기반 오류 응답을 사용한다. CSRF Token은 전용 API에서 받아 메모리에만 유지하고 외부 효과가 있는 명령은 `Idempotency-Key`, 모든 응답은 `X-Request-Id`로 추적한다.
87. **화면 와이어프레임:** 공개·가입·일반·그룹 관리·전체 관리와 오류 화면별 Markdown 와이어프레임을 `docs/design/wireframes/`에 관리하고 화면 설계서의 경로표에서 직접 연결한다.
88. **인증·온보딩 API:** OAuth 시도 생성, 공급자 Callback, 가입 문맥·완료, 현재 사용자, 로그아웃과 초대 수락·거절 Endpoint를 분리한다. Callback은 인가 코드나 공급자 Token을 CSR URL에 노출하지 않는다.
89. **아바타 과시 요구:** 아바타 아이템을 주 수입원으로 보고 다른 사용자에게 장착 결과를 보여줄 수단을 제공한다. 기본 방향은 크리처 홈에서 현재 접속한 그룹 구성원의 아바타가 공동 크리처 주변을 돌아다니는 구성이다.
90. **그룹 정원 산책:** 크리처 홈에 접속 중인 그룹원의 장착 아바타를 최대 20명 표시하고 선택 시 기여·순위·장착 상품과 상점 이동을 제공한다. WebSocket은 접속·퇴장·장착 변경만 전파하며 이동은 클라이언트 자동 애니메이션으로 처리한다.
91. **WebSocket 동기화:** `/ws`의 그룹 STOMP 채널에서 Presence·장착·크리처·기여 이벤트를 전달한다. 구독 후 REST Snapshot을 적용하고 Stream 식별자나 Sequence가 바뀌면 재조회하며 연결 실패 중에는 30초 Polling으로 대체한다. 연결 상태는 헤더의 프로필 앞에 표시한다.
92. **그룹·게임 API:** 공개 그룹·멤버십·권한·초대, 현재 시즌·활성 크리처 종 목록·크리처 선택, 퀘스트 완료·체크인·필수 EXIF 사진 제출과 개인·그룹 랭킹 Endpoint를 `/api/v1` 아래에 구성하고 모든 명령이 최신 권한·상태·정원을 재검사한다.
93. **포트원 V2 카카오페이 결제:** 테스트 결제 공급자는 포트원 V2, PG 채널은 카카오페이 하나로 확정한다. `EASY_PAY`·`KRW`만 요청하고 브라우저 SDK 결과를 신뢰하지 않으며, 서버가 결제 단건 조회로 상태·Store·금액·통화를 검증한다. `PaymentGateway` Port와 포트원 Adapter를 분리해 다른 공급자로 확장할 수 있게 한다.
94. **결제·환불·관리 API:** 상점·장착, 주문·결제 검증·Webhook, 환불 승인·결과 복구, 신고와 관리자 집계 Endpoint를 `/api/v1` 아래에 구성한다. Webhook과 브라우저 완료는 같은 멱등 정합성 서비스를 사용한다.
95. **DTO·업무 오류:** 명령 DTO는 서버 판단에 필요한 식별자·사유·명시적 확인만 받고 클라이언트 계산값을 받지 않는다. 응답은 Entity·공급자 DTO를 노출하지 않으며 업무 오류 코드는 Endpoint와 관계없이 같은 HTTP 상태와 의미를 유지한다.
96. **Vanilla JS·Bootstrap:** 프론트엔드는 Vite 기반 Vanilla JavaScript ES Module과 Bootstrap v5.3 계열로 구성한다. 기본 History API Router와 Route Guard 구현은 스피어 프로토콜의 공통 기반 구현 대상으로 이관한다.
97. **프론트 모듈 생명주기:** `pages`, `features`, `components`, `api`와 외부 연동 모듈을 분리한다. 각 Route Page는 `mountPage(context)`와 Cleanup 함수를 사용하고 이동 시 요청·Event·Timer·WebSocket·Bootstrap Instance를 해제한다.
98. **백엔드 구조와 트랜잭션:** 기능 중심 패키지를 기본으로 하고 복잡한 영역만 `api`, `application`, `domain`, `infrastructure`로 나눈다. 외부 Port 호출은 DB 트랜잭션 밖에서 수행하고 처리권 선점·외부 호출·결과 확정의 세 단계로 분리한다.
99. **DTO·검증 자율성:** 요청·응답 DTO는 일반 `class` 또는 Java `record`를 자율적으로 사용하고 입력 검증도 Bean Validation 또는 명시적 `validate()`를 선택할 수 있다. 최신 DB 상태가 필요한 업무 검증은 Service가 담당한다.
100. **초심자 중심 프론트엔드:** Vanilla JavaScript 화면은 Router 선택, API 호출, DOM 표시·Event 연결, Cleanup의 반복 구조로 설명하고 기존 Page를 따라 작성할 수 있게 한다. 프론트엔드 자동 테스트 Framework는 필수로 두지 않는다.
101. **단순화한 테스트:** Docker·Testcontainers를 사용하지 않는다. 백엔드는 JUnit 5와 로컬 MySQL 테스트 DB로 핵심 업무·동시성만 자동 검증하고, 프론트엔드는 API 응답과 같은 목 데이터를 켜 브라우저 체크리스트로 검증한다.
102. **포매팅·환경:** SQL 콤마 위치와 정렬은 팀원 자율로 하되 쿼리 내부 일관성을 유지한다. `local`, `test`, `integration`, `prod` Profile을 사용하고 비밀값은 환경변수로 관리한다.
103. **클래스 책임 분리:** 클래스 다이어그램은 인증·그룹, 시즌·퀘스트·랭킹, 아바타·결제·환불, 공통 기반·실시간·동시성의 네 영역으로 분리한다. Controller는 HTTP, Service는 업무 규칙·트랜잭션, Repository는 영속성, Adapter는 외부 연동을 담당한다.
104. **ERD:** 40개 업무 테이블을 계정·그룹, 시즌·랭킹, 퀘스트·활동, 결제·아바타, 운영 공통의 5개 Mermaid ERD로 분리하고 PK·주요 FK·상태·UNIQUE 판단 키와 영역 간 관계를 표시한다.
105. **요청 추적성:** 사용자 시나리오와 업무 규칙에 변경하지 않는 `REQ-{영역}-{번호}` 32개를 부여하고 화면 경로와 API Operation이 해당 번호를 직접 참조한다.
106. **API 필드 계약:** 58개 Endpoint마다 Operation ID, 요청 ID, Path·Query·Header·Body와 성공 응답 DTO를 정의한다. 모든 요청 필드는 타입·필수·길이·정규화·허용값을, 응답 필드는 타입·Null 가능 여부·의미를 명시한다.
107. **시즌 종료 작업:** `SEASON_CLOSE`가 시즌을 `CLOSING`으로 선점하고 크리처 보관과 최종 랭킹 Snapshot을 멱등 생성한 뒤 `ENDED`로 확정한다. 같은 시각의 다음 시즌 시작은 종료 확정 후 실행한다.
108. **최소 LLM 연동:** 새 그룹 소개 입력에서만 Gemini 문장 교정을 요청한다. 최대 500자의 원문을 서버가 전달하고 구조화된 교정 문장 하나만 받아 사용자가 선택적으로 적용한다. 결과는 자동 저장하지 않으며 실패해도 원문으로 그룹을 생성할 수 있다.
109. **LLM 보안·테스트:** Gemini API Key와 모델 설정은 서버 환경변수로 관리하고 교정 본문은 DB·로그에 저장하지 않는다. 공급자 호출은 `TextProofreader` Adapter로 격리하고 테스트에서는 Fake를 사용한다.
110. **주 관리자 이전 결과:** 다른 활성 회원에게 주 관리자 권한을 이전하면 대상은 `PRIMARY`, 기존 주 관리자는 `MEMBER`가 되며 기존 부 관리자 권한을 유지하지 않는다.
111. **현재 사용자 상태 조합:** `/api/v1/me`는 익명 `ANONYMOUS + NOT_STARTED`, 가입 대기 `SIGNUP_PENDING + SIGNUP_REQUIRED`, 그룹 선택 필요 `AUTHENTICATED + GROUP_REQUIRED`, 온보딩 완료 `AUTHENTICATED + COMPLETED` 조합을 반환하고 Route Guard가 이를 고정 매핑한다.
112. **PG 거래 식별자:** 내부 주문번호 `paymentId`는 `purchases.order_number`에만 유지한다. 승인 행에는 포트원 거래 객체 ID, 취소 행에는 `cancellation.id`를 저장하고 `(provider, provider_transaction_id)` 복합 UNIQUE를 적용한다.
113. **멤버십 공통 잠금 순서:** 가입·탈퇴·강퇴·역할 변경·주 관리자 이전은 영향 사용자 ID 오름차순 → 그룹 → 관련 멤버십 ID 오름차순 → 가입 제한 순으로 잠가 상호 경합과 교착을 방지한다.
114. **기존 회원 초대 수락:** 그룹 없는 기존 회원은 초대 수락 시 링크·정원·24시간 제한을 재검사하고 대상 그룹에 즉시 가입한다. 실패하면 그룹 없는 계정과 세션을 유지하고 이유를 표시한다.
115. **회원가입 대기 시간:** 신규 사용자의 가입 대기 세션은 OAuth 콜백 완료 시점부터 고정 30분 동안 유효하다. 만료 시 계정을 생성하지 않고 대기 정보를 제거한 뒤 로그인부터 다시 시작한다.
116. **Java 기준 버전과 Package:** 백엔드의 로컬 개발, Gradle Toolchain과 CI 실행 환경을 Java 21 LTS로 통일한다. 기준 Package는 `com.team.sharedcreature`이며 현재 초기 소스와 일치한다.
117. **서비스 표시명:** 사용자 화면, 브라우저 제목과 OAuth 애플리케이션 표시명은 `다 같이 키우는 생명체`를 사용한다. 저장소·Artifact·프로젝트 Name은 `shared-creature-game`으로 유지한다.
118. **테스트 결제 채널:** 포트원 V2의 카카오페이 테스트 채널만 사용한다. 결제 요청은 `EASY_PAY`·`KRW`로 고정하고 PC는 IFrame, 모바일은 Redirect 방식을 사용하며 전체 취소만 지원한다.
119. **EXIF 핵심 범위:** 위치·촬영 시각 EXIF 사진 인증과 `photo_submissions`는 MVP 핵심 필수 기능이다. Android Chrome과 iOS Safari 검증 실패는 제외 사유가 아니라 MVP 미완료이며, 사진 템플릿은 중 난이도 활성 순회에 포함한다.
120. **EXIF 이미지 형식:** 최대 10 MiB의 JPEG만 지원한다. 서버가 `image/jpeg` MIME 형식과 JPEG Signature를 함께 확인하고 HEIC·HEIF 등 다른 형식은 `PHOTO_FORMAT_UNSUPPORTED`로 거절한다.
121. **EXIF 최소 판정:** GPS 존재·좌표 유효 범위와 촬영 시각의 배정 기간 포함 여부만 검증한다. Offset 없는 EXIF 시각은 `Asia/Seoul`로 해석하며 실외·현재 위치·장소·거리·위변조·사진 재사용은 판정하지 않는다.
122. **초보자 구현 가능 API 계약:** 58개 Operation마다 입력 위치·DTO·성공 응답뿐 아니라 성공 HTTP 상태와 업무 오류를 연결한다. Endpoint별 Query DTO, 고정 정렬, 공통·Page·Rank Meta, 오류 필드, OAuth Redirect, PortOne Webhook 소비 필드와 Vanilla JS 호출 예시를 상세 정의한다. 사진 제출은 POST 안에서 최종 판정해 별도 조회 API를 추가하지 않는다.
123. **설계에서 코드까지의 연결:** 구현 시작 안내서에 요청 ID → 화면 → Operation ID → DTO → Service·Repository·테이블의 고정 추적 순서, 기능 화면별 API 연결표, 기능별 백엔드 시작점, 목 데이터 작성법과 백엔드·프론트엔드 완료 체크리스트를 제공한다. 상세 계약은 기존 원문 설계서를 링크해 중복 정의하지 않는다.
124. **1인 그룹 종료:** 주 관리자가 유일한 구성원이면 기존 탈퇴 동작이 그룹·초대 링크·현재 시즌 참여를 함께 비활성화하고 24시간 가입 제한을 적용한다. 기록은 보존하며 별도 해산 API는 만들지 않는다.
125. **환불 고착 복구:** 5분 이상 지속된 `CANCEL_PENDING`은 5분 주기 복구 작업이 PG 상태를 먼저 조회하고 기존 멱등 키로 완료·재시도·실패·결과 불명 상태를 확정한다.
126. **Webhook 복구:** 5분 이상 지속된 Webhook `PENDING`과 `FAILED`는 PortOne 최신 결제를 조회하고 기존 결제 정합성 Service로 복구한다.
127. **사진 마감:** 촬영·업로드 접수 시각이 배정 기간 안이고 판정·보상 Commit이 마감과 시즌 종료 선점 전에 완료돼야 보상하며 유예와 이월은 제공하지 않는다.
128. **미접속 강퇴 안전 여유:** 활동 시각의 최대 10분 영속화 지연을 고려해 저장값 기준 72시간 10분 경과 후 강퇴를 허용한다.
129. **주간 활동 귀속:** 기간 집계는 완료 시점과 같은 멤버십·그룹 시즌에서 발생한 활동만 사용하고 이전 그룹 활동을 새 그룹 보상으로 이전하지 않는다.
130. **OAuth 시작 세션 귀속:** OAuth 시도에 시작 익명 세션 ID의 Hash를 보관하고 Callback 세션이 다르면 `OAUTH_SESSION_MISMATCH`로 중단한다. 성공 후에는 인증 세션 ID를 교체한다.
131. **WebSocket 인바운드 기본 거부:** 세션·Origin·CSRF를 확인한 STOMP `CONNECT`, 현재 활성 그룹의 `SUBSCRIBE`, 현재 연결 구독의 `UNSUBSCRIBE`, 정상 `DISCONNECT`만 허용한다. 클라이언트 애플리케이션 `SEND`·`MESSAGE`는 모두 거부한다.
132. **외부 요청 호출량:** OAuth 시작은 세션당 10분 5회·IP당 10분 30회, Gemini는 사용자당 1분 5회·KST 하루 30회·전체 동시 2건으로 제한한다. 단일 인스턴스 메모리 제한은 재시작 시 초기화를 허용한다.
133. **사진 처리 자원:** 사진은 사용자·배정당 5회, 사용자당 1분 5회로 제한하고 EXIF는 최대 1 MiB·동시 4건·5초 Timeout으로 메타데이터만 읽는다.
134. **통합 HTTPS 검증:** 평상시는 localhost HTTP와 `local` Profile을 사용한다. 모바일 OAuth·결제 Redirect·Webhook·실기기 사진 통합 검증 때만 제품을 고정하지 않은 임시 HTTPS 터널과 `integration` Profile을 사용하며 운영 HTTPS 구축은 범위에서 제외한다.
135. **포트원 취소 매핑:** `SUCCEEDED → COMPLETED`, `FAILED → FAILED`, `REQUESTED → CANCEL_PENDING`으로 변환하고 `REQUESTED`는 Webhook 또는 재조회 전까지 완료로 간주하지 않는다.
136. **최초 전체 관리자:** 공개 생성 API나 역할 입력 필드를 두지 않고 활성 전체 관리자가 없을 때 환경변수의 공급자·불변 공급자 사용자 ID와 정확히 일치하는 신규 계정만 `SUPER_ADMIN`으로 생성한다. 기존 일반 회원은 자동 승격하지 않는다.
137. **자원 인가 응답:** 다른 사용자의 구매·보유 아이템·환불 개별 자원은 `404`로 존재를 숨기고, 존재하는 그룹·전체 관리자 기능의 역할 부족은 `403`으로 응답한다.
138. **경로 접근 등급:** Route Guard는 사용자 상태와 `PUBLIC`, `AUTHENTICATED`, `GROUP_MEMBER`, `GROUP_ADMIN`, `SUPER_ADMIN` 경로 등급을 함께 평가한다. 그룹 없는 일반 회원도 로그인 전용 화면은 사용할 수 있고 그룹 없는 전체 관리자는 `COMPLETED` 상태로 관리자 화면에 접근한다.
139. **Webhook 복구 식별자:** 서명 검증된 결제·취소 이벤트의 `paymentId`를 별도 컬럼에 먼저 보존해 내부 주문 식별 전에 실패해도 복구할 수 있게 한다.
140. **랭킹 현재 대상:** 랭킹 응답은 `meta.currentSubject` 키를 항상 제공하고 대상이 없으면 객체 전체를 `null`로 반환한다.
141. **로컬 DB 전환:** 스피어 실행에서 H2 기반 `local` 설정을 MySQL·`ddl-auto=update`로 바꾸고 별도 MySQL 테스트 DB는 `create-drop`으로 사용한다.

### 구현 단계에서 확인할 사항

- 카카오페이 테스트 채널에서 실제로 관찰되는 PG 오류 코드의 내부 표준 오류 매핑 검증.
- JPEG EXIF 핵심 기능의 Android Chrome·iOS Safari 실기기 촬영·업로드 검증 결과.
- 임시 공개 HTTPS 주소에서 Google·Naver Callback, PortOne 모바일 Redirect·Webhook과 WebSocket 연결 검증 결과.
- 선택한 `GEMINI_MODEL`의 구조화 출력, Timeout과 실제 할당량 검증 결과.

위 항목은 확정된 설계를 바꾸는 정책 결정이 아니라 실제 외부 환경에서 확인하고 결과를 기록할 구현 검증 항목입니다.

## 12. 발표·면접용 소개문

> 저희는 일상의 작은 활동을 지속할 계기가 부족하거나, 낯선 사람과의 적극적인 교류가 부담스러운 사람에게 게임을 통한 참여 동기를 제공하고자 했습니다. 서비스에 가입한 사용자들은 그룹에 참여하여 일일·주간 퀘스트를 수행하고, 하나의 공동 크리처를 성장시키며 그룹 내 개인 기여도와 그룹 간 성과로 경쟁합니다. 기상 체크인과 GPS 메타데이터를 이용한 야외 사진 인증 등 현실 활동에 연결되는 퀘스트도 제공하고자 합니다.
>
> 기술적으로는 Spring Boot와 MySQL을 기반으로 퀘스트 및 성장 상태를 관리하고, WebSocket으로 결과를 실시간 공유합니다. 여러 사용자가 동시에 보상을 받는 상황에서 데이터 정합성을 보장하고, 크리처 성장과 분리된 아바타 꾸미기 아이템에 PG 테스트 결제·사용 여부 기반 환불을 구현하여 웹 서비스의 핵심 기능을 경험하는 것이 목표입니다.
